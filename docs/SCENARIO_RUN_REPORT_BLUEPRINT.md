# Blueprint — Model Scenario Run Report

*Design only. A single, comprehensive stats report produced alongside every
TSM v6 scenario run, from population synthesis through assignment, as a
self-contained HTML page (and a markdown twin).*

## 1. The idea

Today each step writes its own scattered outputs (CSVs, gpkgs, a validation
workbook). Nobody sees the scenario as a whole. The proposal: a **scenario
report card** — one HTML file, generated automatically when a run finishes (or
on demand from the panel), that walks the entire pipeline and reports the
metrics that tell an analyst "is this run reasonable?" at a glance, with real
charts. Think of the HyDRA demo page's production quality, applied to the full
model chain and generated by script from the run's own outputs.

Two artifacts, same content: `scenario_report.html` (charts, shareable) and
`scenario_report.md` (diffable, drops into a PR or a memo). Both from one
Python generator reading the run directory.

## 2. The pipeline and the metrics for each stage

The report is a sequence of sections, one per model step, each reading that
step's output files.

### 2.1 Population synthesis (PopSyn)
*Source: synthetic households/persons, control totals.*
- Households and persons synthesized, by county; totals vs control marginals.
- **Marginal fit**: for each control (HH size, income, age, workers), a
  observed-vs-synthesized bar pair and a % deviation — the classic PopSyn
  validation. Flag any marginal off by > a threshold.
- Persons per household distribution; income distribution.

### 2.2 Skims (Skimmy)
- Skim coverage: zones, skim matrices produced, any unreachable OD pairs.
- Free-flow vs congested skim summary (if a warm skim exists); mean/percentile
  travel times by market.
- Sanity: intrazonal shares, max/min skim values (catch bad connectors).

### 2.3 Short-Distance Travel (SDT) — resident + visitor
*Source: `sdt_resident_trips`, `sdt_visitor_trips`.*
- Trips by **purpose** (HBW, HBO, NHB, …) and by **mode**.
- **Trip length frequency distribution** (the key SDT diagnostic) vs a target
  curve, per purpose — a line chart with the observed/target band.
- Time-of-day departure profile (and the note that the post-COVID clock is
  deliberately flat — the report should show it, not flag it as wrong).
- Trip rate per person / per household vs expected.
- Resident vs visitor split; visitor trips by segment (air/highway/etc.).

### 2.4 Long-Distance Travel (LDT) — resident + visitor
*Source: LDT resident/visitor tours, DMA-to-DMA summaries.*
- Tours by purpose and mode; auto vs air share.
- **DMA-to-DMA matrix** heatmap (intra- vs inter-DMA share) — the LDT
  calibration surface.
- Trip length distribution for LDT (the > 50-mi tail).
- External / cross-border volumes vs the station targets.

### 2.5 Trip list assembly (agentPlans)
*Source: the assembled `tripList` handed to assignment.*
- Total person-trips → vehicle-trips (via occupancy); the vehicle count.
- By **market / VOT segment**, occupancy, and vehicle type (the new EL-choice
  levers) — so you can see the truck and EV shares that will drive tolling.
- Departure-time profile of the final loaded demand.
- Any trips dropped (bad OD, unreachable) with counts.

### 2.6 Assignment (HyDRA)
*Source: run console, `link_performance_*`, `count_validation`, agent stats.*
- **Convergence**: the relative-gap trajectory over iterations (the
  non-monotone progressive-sampling curve), final gap, iterations, runtime,
  peak memory.
- **Network totals**: VMT, VHT, mean network speed, by facility class.
- **Count validation**: model/observed ratio, R², %RMSE, GEH < 5 / < 10 —
  overall and **by facility class and by county** (tables + scatter). This is
  the headline validation.
- **Tolling**: EL toll-rate profiles, EL share, revenue proxy, by corridor.
- **Multi-resolution**: meso queue/breakdown summary; micro corridor
  completion, EL/GP speeds, delay — where a micro run was included.

## 3. Cross-cutting: the scenario header and comparison

- **Header card**: scenario name, network (link/node counts), demand
  (person/vehicle trips), config digest (macro model, meso/micro extents, toll
  policies), hardware, wall-clock, date. A one-line provenance so a stored
  report is self-describing.
- **Scenario compare (phase 2)**: point the generator at two run directories →
  side-by-side deltas (Δ VMT, Δ gap, Δ EL share, Δ count R²) so a "what changed"
  review is one command. This is where the report earns its keep for scenario
  planning.

## 4. Generation mechanism

- A single `scenario_report.py` (QGIS Python or standalone, matplotlib +
  a templated HTML) that takes `--run-dir` (and optionally the upstream
  demand-output dirs) and writes `scenario_report.{html,md}` plus a
  `figures/` folder of PNG/SVG (reusing `make_demo_figures.py`'s generators
  where they overlap — segment/movement/EL/probe/toll are already scripted).
- **Self-contained HTML**: inline CSS + inline SVG charts (the demo-page
  pattern), theme-aware, no external assets — so it opens anywhere and attaches
  to a memo.
- **Robust to missing steps**: each section checks for its inputs and renders
  "not run" rather than failing, so a demand-only or assignment-only run still
  reports what exists.
- **Metrics table sidecar**: every chart's underlying numbers also written to
  `scenario_metrics.csv` (one tidy long table: stage, metric, segment, value)
  so the report is queryable and diffable, not just visual.

## 5. Integration with the panel and the run

- **Auto-produce**: the Summarization step (or a run-complete hook) calls the
  generator so a report lands with every full run, no extra action.
- **On-demand**: a "Scenario Report" button in the Analyst group opens a small
  dialog (pick run dir + optional demand dirs + output path) and renders it.
- **Standard metrics contract**: fix the `scenario_metrics.csv` schema so the
  report, the dashboards (see the limited-access dashboard blueprint), and any
  external tracking read the same numbers.

## 6. Build phases

1. `scenario_metrics.csv` schema + the assignment section (reuses existing
   figure generators + count validation). Delivers the highest-value half.
   **DONE** — `Apps/Report/scenario_report.py` reads a run dir and writes
   `scenario_report.html` (self-contained, inline CSS + **static inline SVG**
   charts that theme via CSS vars — no JS charting, no external assets),
   `scenario_report.md` (diffable twin), and `scenario_metrics.csv` (tidy long:
   stage,section,metric,segment,value,unit). Assignment section covers: header/
   provenance card; network totals (VMT/VHT/volume-weighted mean speed by
   facility, summed over the disjoint tiers, length = speed×tt, connectors
   dropped); count validation (canonical `valstats`: model/obs ratio, R², %RMSE,
   GEH<5/<10 — overall + by facility + by county, with obs-vs-model scatter and
   ratio pills); tolling (EL toll profile, peak, revenue proxy); convergence
   proxy (weighted gap÷cost) + resolution split. Demand sections render
   "not run — phase 2–3". Metric formulas match `model_performance_summary.py`.
   Verified on exp_tri_tollcmp (102 metrics; both themes render; the by-county
   table correctly exposes it as a tri-county subarea run).
2. Demand sections (SDT/LDT trip-length + DMA + mode/purpose) and the trip-list
   section. **DONE** — chunked+cached trip-list aggregation (market composition,
   VOT, purpose, market×purpose, occupancy clamped [1,8] against raw outliers,
   departure profile) + SDT/LDT subsections via the market tag (string labels,
   no code-map guessing). Trip-length/DMA heatmap remain refinements needing
   the raw SDT/LDT files with code maps.
3. PopSyn + Skims sections; the header/provenance card. **DONE** — PopSyn:
   expansion-weighted HH/persons vs tsm_landuse control totals (overall + top-12
   counties, deviation pills), HH-size distribution. Skims: coverage sanity ONLY
   (zones / disconnected ODs / isolated fallbacks) — the skim is free-flow, so
   OD-time stats are deliberately not reported (user ruling 2026-07-11).
   Sections ordered along the pipeline: PopSyn → Skims → SDT → LDT → trip list →
   assignment (user request).
4. HTML polish + panel button + run-complete auto-hook. **DONE (button)** —
   "Scenario Report" button added to the Analyst group in code (the .ui has no
   placeholder), opening `scenario_report_plugin.ScenarioReportDialog` (run dir,
   demand dir, title, min-mainline, open-when-done). Run-complete auto-hook
   deferred until the HyDRA runner has a completion callback to attach to.
5. Scenario compare (two-run deltas). — open

## 7. Why HTML + markdown, not just Excel

Excel is a data dump; the report is a **narrative with validation charts** that
a reviewer reads top-to-bottom to judge a scenario. HTML gives the charts and
shareability; markdown gives the diff and the memo paste. The tidy
`scenario_metrics.csv` covers the "I want the raw numbers in a spreadsheet"
case and feeds the dashboards. (The daily-volume dashboard is a separate,
map-driven, drill-down tool — see its own blueprint.)
